# AI工程机制术语表

本词表适用于当前包，机制版本见[Skill元数据](../SKILL.md)。

本文件统一本 Skill、指南和模板 的方法术语。本文件定义方法术语；首版已实现的字段和命令以 cli.md 为准，未实现状态不表示已有程序支持。

同一概念使用一个标准名称；不同概念不得共用一个状态或字段。项目自己的业务、产品和技术概念由项目 `docs/glossary.md` 或现有等效文件维护，引用本机制术语时不另行改变含义。

## 1. 体系、角色与文件

| 标准术语 | 明确含义 | 用法与边界 |
|---|---|---|
| AI工程机制（ai-sdlc） | 支持 AI 与人推进项目的一组文件约定、任务流程、验证、记录和参与规则 | 本项目现行名称；旧标识 ai-project-harness 保留作历史对应，SDLC 指软件开发生命周期。旧称“项目开发机制（Project Harness）”保留作历史对应。“项目开发机制”也可泛指此类方法；“脚手架”仅作通俗解释，不单指目录或代码生成器 |
| Skill | 封装可复用方法、模板和可选脚本的能力包 | 不等同于项目规则、事件执行器或执行成功证据 |
| 开发 AI | 在当前授权内修改项目、执行验证、维护记录的 AI | 取代 coding AI、coding agent；主体为项目开发者 |
| 产品内 AI | 产品运行时参与用户功能的 AI | 不因能执行产品任务而获得项目写入、修改验收或发布权限 |
| 项目负责人 | 对项目目标及授权边界承担决定责任的人 | 具体事项可按项目约定交给对应负责人；不要求所有日常操作由其批准 |
| 执行器 | 实际执行命令并保存执行结果的程序或平台组件 | 与开发 AI 的推理、自然语言承诺分开 |
| 项目入口 | 帮助人和 AI 找到当前规则、任务、运行方式的入口文件 | 默认 `README.md`；入口不重复维护所有正文 |
| 规则维护位置 | 某项规则正文唯一持续维护的文件或章节 | 替代“属主”；维护位置是文件，维护责任是人或开发 AI，二者分开 |
| 现行规则来源 | 在相应范围内已经按项目授权确认、当前有效的规则文件或章节 | 替代笼统的“权威”；候选文件存在不表示已确认，同一范围避免竞争来源 |
| 项目映射 | 将本机制的职责对应到项目实际文件、章节、命令及工具 | 已有等效位置优先复用；不要求强制改成模板路径 |
| 模板 | 含结构、说明及待填内容的复用样本 | 不能当作项目事实、已确认规则或执行证据 |
| 项目记录 | 在具体项目中填写的任务、计划、决定或实验记录 | 与模板分开；“实例”只在说明模板与填好记录的关系时使用 |

## 2. 产品规则与开发流程

| 标准术语 | 明确含义 | 默认维护位置 |
|---|---|---|
| 需求 | 产品面向谁、解决什么问题、目标及范围是什么 | `docs/requirements.md` 或项目映射位置 |
| 产品行为规则 | 产品运行时，给定用户操作、产品状态、数据或失败条件，应发生什么结果及例外 | requirements；规模较大时拆到 `docs/rules.md`，涵盖业务和玩法 |
| 开发执行规则 | 开发 AI 如何接手、修改、验证、同步记录、交接及遵守授权 | `AGENTS.md` 及对应验证、开发环境文件 |
| UX 规范 | 用户操作、界面反馈、布局、视觉和可访问性约定 | `docs/ux-guidelines.md` 或项目映射位置 |
| 设计变量 | 在代码或设计系统中复用的颜色、字体、间距等取值及名称 | 不与模型输入输出的 token 数混用 |
| 验收标准 | 判断声明范围内的结果是否满足目标的具体条件 | 需求等现行规则来源；任务记录引用或在授权内补充本任务标准 |
| 验证策略 | 按风险确定检查范围、命令、环境、时机、证据失效及人工验收边界的规则 | `TESTING.md` 或现有等效来源 |
| 比例验证 | 选择足以支持当前结论的最小验证范围，并按具体条件升级 | 依次考虑定向检查、受影响回归、满足触发条件时的全量检查 |
| 专项检查 | 按某一类最低清单检查声明范围，并逐项记录覆盖、发现和处置 | 流程入口在 maintenance.md；新增检查不替代必需项 |
| 阶段健康检查 | 在阶段节点对声明范围执行五类基础专项，并判断实验与UX两个条件专项，适用者纳入 | 完整检查不等于逐行审查或全量测试；扫描完成与健康检查通过的条件按 maintenance.md |
| 术语体系检查 | 核对概念及词表增删改，再按有效词表扫描、授权修复并复验 | 流程在 terminology-review.md；不以文本替换代替概念判断 |
| 条件专项 | 按当前任务或阶段的能力、变化及结论选择的专项；适用时其必需项进入检查范围 | experiment-review.md、ux-review.md；不表示可任意省略，缺环境不等于不适用 |
| 实验与评价检查 | 核对实验问题、设计、评价、执行及结论是否支持当前决定 | experiment-review.md；区别于记录一次实验，也不强制所有探针采用对照实验 |
| 用户体验检查 | 依据目标用户、项目UX标准和实际界面检查任务可用性 | ux-review.md；区别于定义UX规范，不指定设计风格或全组合穷举 |
| 验证 | 收集和核对事实，以判断结果是否符合所选标准的活动 | 包括测试、静态检查、实际环境观察等；不凭 AI 自述作结论 |
| 测试 | 使用确定输入、操作及预期结果检查行为的一类验证活动 | 是验证的一部分，不代表所有质量和实际环境要求 |
| 消费者 | 使用被修改模块、接口、数据或生成物的代码及流程 | 用于确定受影响回归范围；不是泛指产品用户 |
| 人工验收 | 指定的人依据具体材料，对要求由人判断的结果作出接受或不接受的决定 | 人工验收是验收判定的一部分；自动验证不能虚构人的确认 |

“规则”“行为”“状态”“验收”在已明确主体和范围的段落中可以简写；标题、字段和跨文档指令必须明确对象。禁止将“复杂行为规则”作为独立分类而不说明产品或开发主体。

## 3. 任务与证据

| 标准术语 | 明确含义 | 用法与边界 |
|---|---|---|
| 开发任务 | 当前授权内的一项有明确目标、范围、验收标准及下一动作的工作 | 后文可简写“任务”；与产品用户任务分开 |
| 任务范围 | 本任务允许修改、需要满足的条件及明确非目标 | 替代含义不明的“本批”；项目原有批次制度照其自身定义映射 |
| 任务记录 | 保存任务范围、执行状态、决定、证据和下一动作的唯一详细记录 | 例如 `docs/tasks/TASK-001.md`；编号与文件名按 [cli.md](cli.md#任务编号与文件命名)；替代“工作单” |
| 实施计划 | 复杂任务的步骤、依赖、检查点、中断条件及恢复方法 | 单任务步骤在任务章节；跨任务阶段计划按依赖与检查点复杂度拆分，引用任务记录；计划确认不改变授权或完成状态 |
| 决策记录 | 保存重要决定的背景、方案、理由、确认来源和替代关系 | 不替代需求或架构的当前规则正文 |
| 实验记录 | 保存未证实假设、条件、预算、停止条件和观察结论 | 实验执行完成不表示假设成立或产品通过验收 |
| 状态入口 | 当前任务链接、事实摘要、下一动作和待人事项的入口 | 默认 `docs/status.md`；详细任务执行状态由任务记录维护 |
| 验证执行记录（RUN） | 一次检查执行的命令、对象、版本、环境、输出、退出码及时间 | RUN 编号只标识执行记录，不表示通过；未执行样例没有真实 RUN 证据 |
| 执行回执 | 执行器记录的一次触发或动作是否实际执行及其结果 | 替代“收据”；格式合规仍需核对真实来源、对象与结果 |
| 验证证据 | 能支持具体结论的执行记录、日志、观察结果及必要材料 | 证据必须说明支持范围；不是所有回执都能支持验收结论 |
| 证据有效性 | 某份证据对当前所声明对象、版本、环境及标准是否仍适用 | 与原执行是否通过分开；源码变化不会改写原始执行结果 |
| 交付 | 将具体结果及其说明、证据和限制提供给用户或后续执行者 | 交付可包含部分完成结果，不自动表示任务完成、人工验收通过或发布 |
| 交付检查 | 交付前核对验收标准、实际差异、相关有效证据、文档及剩余事项的动作 | 缺必需条件时不得宣称任务完成；独立完成范围可据实交付 |
| 任务收尾 | 更新任务记录、状态入口、剩余事项归属并说明任务执行状态 | 完成、取消及中断都可做收尾；收尾不等于完成 |
| 任务完成 | 当前声明的任务范围内，必需实现、验证及其他完成条件均已满足 | 人工验收若是该任务必需条件，待确认时任务不能标完成；若另属后续产品验收，须明确任务范围及后续归属 |
| 交接 | 将当前事实、有效依据、证据、下一动作及未决事项留给下一执行者 | “中断交接”与正常交付分开，不把中断写成完成 |
| 原始开发对话 | 最初形成需求、决定或执行结果的那次人机开发交流 | 任务恢复应不依赖重新读取这段对话；不是指本机制讨论本身 |

## 4. 接入、恢复与执行保障

| 标准术语 | 明确含义 | 用法与边界 |
|---|---|---|
| 项目接入 | 在授权内完成职责映射、必要文件建立与填充、规则确认、入口连接和适用检查 | 不能用“已复制模板”代替接入完成 |
| 文件建立 | 实际创建必要目录和文件，或复用并补齐已有等效文件 | 分别记录文件处理结果、内容就绪程度、规则确认状态和检查结果 |
| 规则确认 | 对候选规则按项目现有责任与授权决定是否作为现行规则 | 复用仍有效的确认，不重复批准每项文件 |
| 机制运行验证 | 在实际支持的工具和项目流程中，检查节点是否触发、执行、记录及正确处理缺口 | 文档检查不能证明机制已经运行 |
| 机制校准 | 用已知错误案例及合法变化，检查机制能否发现遗漏并避免误拦 | 首次接入、相关检查逻辑变化、漏检或误拦时按风险执行 |
| 开发任务恢复 | 新会话或执行者根据记录与现场继续原任务 | 核对已完成动作、在途操作和有效证据，不盲目重做 |
| 产品运行恢复 | 产品或服务发生异常后恢复适用运行状态及用户行为 | 方法在开发运行文档，用户结果在产品行为规则 |
| 数据恢复 | 从备份或恢复点取回所需数据，并核对完整性及覆盖边界 | 与 Git 提交、同盘副本、异地备份和开发任务恢复分开 |
| AI 主动执行 | 运行中的开发 AI 根据任务节点自行执行适用步骤 | 不要求用户逐项下命令；不意味着后台事件已经自动配置 |
| 事件触发执行 | 已启用的平台事件实际调用执行器 | 需要核对事件支持、触发回执、超时及失败策略 |
| 强制阻断 | 在具体受控入口，必需条件不满足时实际阻止某项操作 | 必须说明阻止什么、在哪生效、谁控制及绕过路径；规则文字本身不是强制阻断 |
| 提交／合入／发布 | 分别将更改写入 Git 历史、集成到目标分支、向目标用户或环境开放版本 | 是不同操作，各自按项目授权执行；任务完成不自动授权 |

## 5. 状态必须分字段

面向人的文档使用中文标准状态；机器格式使用表中的英文值。现有项目可保留自己的编码，但项目映射须说明等效含义。没有执行器时不得伪造机器输出。

| 状态字段 | 标准状态及机器值 | 判定说明 |
|---|---|---|
| 文件处理结果 | 已创建 `created`、已复用 `reused`、已更新 `updated`、待处理 `pending` | 仅说明文件操作；已复用也需核对真实内容与引用 |
| 规则确认状态 | 候选 `proposed`、当前有效 `active`、已被取代 `superseded`、已停用 `deprecated`、已拒绝 `rejected` | 当前有效必须有对应范围的有效确认或授权来源 |
| 任务执行状态 | 未开始 `not_started`、进行中 `in_progress`、阻塞 `blocked`、已中断 `interrupted`、已完成 `completed`、已取消 `cancelled` | 阻塞表示下一必需步骤缺关键条件；中断表示执行停下但任务未完成；交付不是任务执行状态 |
| 检查执行结果 | 未执行 `not_run`、执行中 `running`、通过 `passed`、失败 `failed`、已跳过 `skipped`、已中断 `interrupted`、执行异常 `error`、结果未知 `unknown` | 全部必需检查跳过不得汇总为通过；执行异常指检查未能正常完成，不直接等同产品行为失败 |
| 验证结论 | 未验证 `unverified`、部分已验证 `partially_verified`、已验证 `verified`、不满足标准 `failed` | 限定具体范围；所需检查未执行或证据不足时不能写已验证 |
| 证据有效性 | 有效 `valid`、已失效 `invalidated`、无法判定 `indeterminate` | 未执行、相关输入标识缺失或证据不可读时无法判定；原结果通过但相关版本已变可标已失效 |
| 人工验收状态 | 不适用 `not_applicable`、待确认 `pending`、通过 `accepted`、不通过 `rejected` | 不适用需范围依据；通过或不通过需指定人的真实决定及材料来源 |

实施计划使用自己的步骤安排状态：草稿 `draft`、执行中 `active`、已暂停 `paused`、已完成 `completed`、已取消 `cancelled`、已被取代 `superseded`。计划状态不能替代任务执行状态。

决策记录使用：候选 `proposed`、已确认 `accepted`、已被取代 `superseded`、已停用 `deprecated`、已拒绝 `rejected`。其中 `accepted` 只表示该决定被确认，不能代替人工验收通过。

实验执行状态使用：已登记 `registered`、执行中 `running`、已完成 `completed`、已停止 `stopped`、已中断 `interrupted`。实验观察结论单独记录：支持假设、不支持假设或证据不足。假设被证伪可以是一次正确完成的实验。

“项目接入完成”是对接入任务条件满足程度的结论，不新增混合状态字段。文件已建立但存在关键未决项时，写“文件已建立；项目接入未完成”，列出缺口、任务执行状态及下一动作。机制运行验证是否执行、支持哪些能力另行记录。

自动化示例保留 `authorities` 作为现行规则来源的路径映射字段；其中 `entrypoint` 和 `status` 是入口路径，不是规则正文。`overall_status` 表示检查执行结果，`verification_status` 表示验证结论，首版 RUN 的 `validity` 表示证据有效性，任务记录的 `human_acceptance[验收ID].status` 表示人工验收状态，四者不得混用。

专项覆盖表使用“已检查无发现、已检查有发现、不适用、未完成”记录条目处置；它们不是上述RUN或任务的机器状态。已检查有发现的条目还须记录发现是否修复及复验，不能把已检查当作通过。

## 6. 不再混用的说法

| 原说法 | 统一写法 |
|---|---|
| 工作单、task 文件 | 任务记录；文件路径可保留 `docs/tasks/...` |
| 本批、批次（未定义） | 任务范围；已有项目正式批次制度按其定义使用 |
| 权威、属主、正式依据（不说明对象） | 现行规则来源、规则维护位置、确认来源；根据实际含义选择 |
| 收据、坏收据 | 执行回执、无效执行回执；说明无效原因 |
| coding AI、coding agent | 开发 AI |
| 产品 agent（未说明主体） | 产品内 AI |
| 人的接受、人接受、等待接受 | 人工验收；状态写待确认、通过、不通过或不适用 |
| 关闭、verified 关闭、done（未说明对象） | 交付检查、任务收尾、任务完成或具体机器字段；按实际动作拆开 |
| 恢复（无主体） | 开发任务恢复、产品运行恢复或数据恢复 |
| 已落实、保障、全自动（无证据范围） | 写明已建立的文件、已执行的动作、实际支持的控制、证据和限制 |

## 7. 规则表述与术语维护

阶段或专项术语检查按 [terminology-review.md](terminology-review.md) 执行：先核对概念及词表增删改，再按有效词表扫描、授权修复和复验。本文件继续维护机制定义，不重复维护检查流程。

操作性规则应能确定**执行者、触发条件、动作、产物、检查方式以及缺口或失败时的处理**；共同上下文已明确的内容直接引用，不要求每条重复六要素。文件更新时机只在其维护规则位置说明。避免仅写“保证质量”“及时同步”“按需检查”而不提供条件和可观察结果。

示例：“准备交付时，开发 AI 按任务记录逐项核对必需验收标准与相关有效证据，填写交付结论并更新状态入口。缺必需证据时列明缺口，保留进行中或阻塞状态；不宣称任务完成。已完成的独立范围可据实交付。”

维护者在机制名称、含义、状态字段或角色边界变化时，先更新本文件，再同步受影响指南、模板、脚本说明和案例；最晚在依赖新术语的编写或执行前完成。模板不要求复制整份术语表，接入时由项目入口记录机制名称、版本和可读取的术语表实际位置。本 Skill 将本文件作为术语参考，不另写竞争定义。

检查应覆盖指南、模板、案例，以及实际创建后的 Skill 入口、参考文件、命令帮助和机器输出。既要查旧称混用，也要查标准词在不同上下文是否仍指同一概念。实际验证范围与证据以开发项目任务记录为准。

## 8. 平台适配与交付检查

任务交付检查命令指 harness.py close；不是 Git 提交、Codex内置命令或平台结束事件。一轮是一次用户消息引出的回应过程，结束不表示开发任务完成。Codex Stop 的自动续轮是平台适配行为，不新增用户授权，也不等同不可绕过的最终交付控制。脚本模式中人的摘要是status/resume派生视图，文档模式按任务事实维护摘要；均不另立详细任务状态。

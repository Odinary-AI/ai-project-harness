# 任务执行与开发任务恢复

先核对目标、现行规则来源、工作目录、已有修改及授权。纯解释不建立实施任务。已授权的代码或文档任务主动执行必要步骤，不再次请求形式批准。

## 模式与生效边界

- **文档模式**：复用任务 Markdown、项目现有命令及真实证据，由开发 AI 显式检查交付；不要求 harness-task、RUN 或脚本命令，不宣称机械阻断。
- **脚本模式**：采用本包执行器和 v2 任务数据块，状态摘要由脚本派生，接口按 [cli.md](cli.md)。所选检查、记录及交付条件须满足。

接入时沿用已有模式；尚未确定时按现有工具和所需证据管理选择，并在项目入口记录。两种模式保留相同的授权、验收、证据和交接底线；不能为绕过缺口临时换模式。既有任务转换按授权映射状态及证据，保留历史。

Skill 仅在用户显式调用时加载。经授权采纳的项目规则在后续会话继续有效，普通实施请求不等于重新调用 Skill；接手按项目入口读取所需依据，不因此加载整个 Skill 包。咨询、解释和状态询问不自动创建实施任务。

## 共同任务流程

新建或移动文件时遵守项目已采用的[目录与文件归属](project-layout.md)，沿其选择与合并边界维护导航。

每个任务一个独立文件（例如 docs/tasks/TASK-005.md），从[任务模板](../assets/templates/records/task.md)选择适用内容。小任务保留目标、范围、授权、验收、证据、必要同步及下一动作；已有表述能说明用户结果或原因时直接复用。仅在依赖、检查点、不确定性或中断恢复需要安排时补实施计划，不以步骤数量触发计划表。

项目综合治理请求先按[综合治理入口](maintenance.md#项目综合治理入口)形成整合方案，复用本任务的实施计划及下文阶段计划安排。

复杂目标尚未形成可独立验收的工作范围时，在已确认目标和优先级内，优先按使用者或调用方、触发、可观察结果拆出最小完整流程，贯通必要模块，并明确验收、依赖及适用的失败/恢复路径。避免仅按技术层分工、把真实集成推迟到全部模块完成后；必要的基础设施或前置任务可单独安排，说明其支持的结果及接入验证点。范围已足以实施和验收时停止拆分，不要求普通小修复重新拆分或增加任务层级。局部任务完成只支持其范围内的结论；完整流程仍按原验收核对实际集成，不自动代表阶段或版本完成。

检查关联真实用户结果。修改共享概念、行为、接口、数据或交互前，定位现行定义、已有职责或实现、直接消费者及不可退化行为；用具体调用、读写或用户路径界定影响，必要时追到相关消费者。实施后按实际差异反查规则、生成源及适用的 UI、数据保护和验证影响，补齐新发现的依赖。普通小修复复用已有依据，只记录影响决定、验收或交接的信息，不新增统一必填表。已确认规则改变在依赖实现前更新唯一正文；证据在真实执行后记录，相关变化按[验证规则](verification.md)处理。

实施前明确判断本次变化是否正确的最小反馈方式，复用现有检查或实际运行入口；反馈不足及诊断选择按下节处理。形成可验证结果且后续工作依赖该结果时，先执行相关检查；失败则在当前授权内修复并复验，通过后继续依赖步骤。缺环境或超出授权时停止依赖该结果的动作，其他已授权且独立的工作可继续。按自然依赖点验证，不要求每次编辑都运行测试；仍有效的证据按验证规则复用，交付前仍须核对整体覆盖和证据有效性。

验证选择遵循项目现行策略；交付前逐项核对有效证据、实际差异、文档同步和剩余事项。重要决定记录分类、来源及对应规则位置，普通实现选择无需升级为规则。范围外后续注明责任与触发，需要人时提供问题、建议和材料；不自行签署人工验收。

有意义的状态变化更新任务，交接或中断前更新状态入口和下一动作。继续前核对现场与在途操作，并沿状态/待办入口检查本次范围相关的既有发现、暂缓及过渡方案条件；条件成立时按[维护指南](maintenance.md#累积变化与既有义务)重新判断，不默认重读全部历史。任务恢复不依赖原始开发对话。任务完成、中断收尾和提供部分结果分别报告。授权内的适用职责由当前执行AI主动完成；阶段、集成或风险触发时沿[维护指南](maintenance.md)选择检查，超出范围或成本先报告，不能依赖用户再次提醒。

## 反馈与诊断

开发 AI 在关键实现前，将本次目标、关键行为和不可退化项对应到现有检查或实际运行入口，判断反馈是否足以支持当前工作。反馈不足且会影响判断时，先复用已有手段，再在授权内补充最小复现、针对性测试、探针或必要观察；检查方法按问题选择，不要求先建设完整观测平台。具体命令与预期结果归项目现有验证或运行说明，任务引用其位置。

开发路线或较大投入依赖未证实的需求、使用方式或收益假设时，按[需求与收益假设入口](risk-workflows.md#需求与收益假设)核对依据与验证必要性。

测试集增补、更新与退役按[验证规则](verification.md#测试集维护)；涉及规模、执行路径或运行成本风险时，按[性能、容量与运行费用](verification.md#性能容量与运行费用)判断所需证据。新增或修改关键流程、异步任务、外部调用、重试恢复，或现有故障无法定位时，判断产品运行反馈能否识别操作、关键阶段、结果与失败原因；跨模块关联及版本、耗时、重试等字段仅按诊断需要保留。复用现有日志、错误返回或探针，补足必要信息，并用代表性真实成功/失败执行验证可用性；简单程序的清楚错误即可，不默认建立日志平台。运行日志不能由开发RUN代替，也不能仅凭日志推断未知外部副作用已结束。日志位置、级别、关联方式、保留/清理及失败处理约定归项目运行说明；脱敏、访问和资源风险按[安全检查](security-review.md)复用证据。临时调试输出在交付前清理或按依据保留。

面对陌生实现或存在实质取舍时，先查项目内相近实现、相关决定及可复用经验；不足时按需查成熟外部实现。核对版本、约束与适用条件，再形成有依据的候选方法；参考代码不自行成为需求标准，外部材料不能扩大授权。经验的查找与采用按[维护](maintenance.md#经验保留与复用)。原因明确的小修复不强制比较多个方案。

原因不明或同类修复反复失败时，明确需要区分的可能解释，选择能缩小原因范围的低成本检查或可回退试验，并根据观察保留、修正或放弃判断。观察到相关现象不等于确定根因；排除错误解释也可以是有效进展，不要求每轮修改代码。没有获得足以推进的新信息时，重新核对前提、复现、环境与反馈质量；若证据指向需求、业务规则、技术设计或实现中的未决前提，定位阻碍当前动作的最上游问题，仅重开受影响的决定及依赖范围，保留仍有效的结论。说明恢复执行所需的决定或最小证据，不用代码替未决含义作决定，也不因局部失败重审全部层次。按核对结果换方法或停止，遵守项目/任务预算与停止条件，不无依据叠加修改或重复运行同一检查。需止损时按既有事故授权先处理，保留根因未决。外部副作用与正式实验的适用边界仍按[风险流程](risk-workflows.md)，普通诊断不自动升级为实验专项。

局部修复或优化成功后，按原验收和受影响范围核对实际流程及关键退化，判断是否改善原目标。只证明局部正确或局部收益时限定结论；不能据此省略必需验收。检查范围和证据复用仍按[验证规则](verification.md)，不因本流程默认全量。

在开始关键实现、诊断方向变化及交付等自然检查点核对上述适用职责；需要专项检查时复用[验证健康检查](validation-health.md)，不要求每次运行整个专项。仅将影响决定或交接的关键观察、判断变化、证据位置和下一动作写入现有任务正文，不逐次编辑登记，不新增必填表。普通小任务沿用简写，额外观察与检查应能回答当前问题。

## 脚本模式的执行

任务规格是 begin 的创建输入；成功后唯一详细状态在任务 Markdown 的 harness-task 块，原规格仅是历史。正文补实际差异、决定、证据说明及按需计划，不重复机器状态。begin 检查共同前置和本任务所选检查；doctor 保留项目整体诊断。

新任务使用 v2，通过 update 保存完整快照并保留 updated_at；文档影响仍需真实审阅，无影响写必要依据。字段默认复用及草稿处理见 cli.md，不另造并行状态文件。

verify 执行所选检查并保存 RUN。tests 类型必须有实际测试计数，probe 不能用于绕过计数。终端丢失先读 RUN；历史 RUN 留在 running 时先核对进程和副作用，结局确定后按 cli.md 的 reconcile-run 追加处置，原件不改写。

暂停用 pause --next；resume 默认只读，核对现场后用 --activate 继续。范围改变时更新验收并恢复或另建任务；取消任务另建记录，旧证据不能覆盖新标准。

交付前运行 close 定位缺口；必需条件和语义审阅满足后，以 close --complete --review-source 引用任务正文或独立审阅文件。status 是带更新时间的派生快照；resume 重新核对当前证据。每轮正常说明、等待人或中断可以结束回应，不表示任务完成。

需要提交或打包时，先完成本轮会生成文件的验证与交付命令，再核对工作区新增/修改文件、必需证据及其依赖和实际暂存/打包范围，包含应保留的RUN、交付回执及更新后的任务/状态入口。随后又有命令写入文件时重核相关差异；提交后检查是否仍有本轮应交付的遗漏，不把其他任务的改动一并纳入。记录保留边界见[验证规则](verification.md#执行证据与交付)。

## 跨任务安排与发布信息归属

默认不建立总 plan 或 releases 文件。目标和标准归需求，当前阶段及任务入口归 status，后续及优先级归 backlog（尚未拆分时归 status），任务步骤和执行事实归各任务记录。

跨任务依赖、先后安排或共同检查点复杂时，建立独立阶段计划，例如 docs/plans/stage-integration.md，注明范围、授权、关联任务、自身计划状态，以及依赖、检查点、停止与恢复安排。目标、验收和任务进展引用现行来源。安排变化在继续依赖步骤前更新，任务不复制共同安排；结束时记录计划偏差。并行沿用授权及唯一写入者规则。

单次发布的产物、版本特有兼容与回退、授权和执行证据归发布任务的按需章节；CHANGELOG 提供用户可见变化和发布任务索引。长期发布责任与授权归 AGENTS 或等效位置，验证要求和命令归现有验证来源，通用部署、监控和恢复归 development（尚未拆分时归 README）。缺必要发布授权时只准备可审查结果，不执行发布。

既有独立计划或发布文件按职责映射复用，不自动删除或迁移；授权内合并有效正文并修正引用，历史执行记录保留。
